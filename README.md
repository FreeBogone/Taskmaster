# Fixx Web Template

A starting point for internal web applications using React, Vite, Tailwind CSS, and shadcn/ui on the frontend; ASP.NET Core, EF Core, and SQL Server on the backend.

This guide describes the default structure for a small-to-medium application. Keep the application in these two projects until there is a concrete reason to split it further.

## Create and run an application

1. In [Gitea](http://git.battery.mfg/Fixx_Web/fixx-web-template), choose **Use this template** and create a repository.
2. Use a C#-safe PascalCase name such as `QualityTracker`. Avoid spaces, hyphens, and underscores because the repository name is also used in project names and namespaces.
3. Clone and run it:

```powershell
git clone http://git.battery.mfg/Fixx_Web/QualityTracker.git
cd QualityTracker
dotnet run --project .\QualityTracker.Server
```

The ASP.NET process starts the Vite development server. Open the client URL printed in the terminal. API documentation is available at `/swagger`.

If the local HTTPS certificate is not trusted, run this once:

```powershell
dotnet dev-certs https --trust
```

## Recommended structure

```text
QualityTracker.Server/
  Controllers/                 HTTP endpoints; no business logic
  Data/
    AppDbContext.cs            EF Core session and DbSets
    Configurations/            Table, relationship, index, and constraint mappings
    Migrations/                Database schema history generated by EF Core
  DTOs/                        API request and response contracts, grouped by feature
    WorkItems/
  Models/                      Database entities
  Services/                    Business rules and database operations, grouped by feature
  Program.cs                   Dependency registration and HTTP pipeline

QualityTracker.client/src/
  app/                         Router, providers, and application-wide setup
  assets/                      Images and other imported static files
  components/
    layout/                    Shared page structure such as header and navigation
    ui/                        Reusable shadcn/ui primitives
  features/
    work-items/
      api.js                   Requests for this feature
      components/              Feature-only UI
      hooks/                   Feature-only state and reusable behavior
      pages/                   Route-level screens
  lib/                         Small application-wide utilities and API helpers
  App.jsx                      Top-level application shell
  main.jsx                     React entry point
```

The normal request path is:

```text
React page -> feature API -> controller -> service -> AppDbContext -> SQL Server
                           <- response DTO <-----------------------
```

Use these boundaries consistently:

- **Controllers** translate HTTP input into service calls and return the correct status code. Keep them thin.
- **DTOs** define the public API. Use separate create, update, and response DTOs so clients cannot set fields such as IDs or audit dates accidentally.
- **Services** own business rules, authorization decisions, queries, and transaction boundaries.
- **Models** describe persisted data. Do not return EF entities directly from controllers.
- **AppDbContext and configurations** own database mapping. A separate repository layer is usually unnecessary because EF Core already provides repository and unit-of-work behavior.

## Configure the database

### 1. Create a model

Create `Models/WorkItem.cs`. Replace `QualityTracker` with the namespace generated for your project.

```csharp
namespace QualityTracker.Models;

public sealed class WorkItem
{
    public int Id { get; set; }
    public required string Title { get; set; }
    public bool IsComplete { get; set; }
    public DateTime CreatedAtUtc { get; set; } = DateTime.UtcNow;
}
```

Keep database concerns such as indexes, maximum lengths, delete behavior, and relationships in classes under `Data/Configurations` as the model grows. `IEntityTypeConfiguration<T>` keeps `AppDbContext` readable.

### 2. Create AppDbContext

Create `Data/AppDbContext.cs`:

```csharp
using Microsoft.EntityFrameworkCore;
using QualityTracker.Models;

namespace QualityTracker.Data;

public sealed class AppDbContext(DbContextOptions<AppDbContext> options)
    : DbContext(options)
{
    public DbSet<WorkItem> WorkItems => Set<WorkItem>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        base.OnModelCreating(modelBuilder);
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);
    }
}
```

Add one `DbSet<T>` for each aggregate that the application queries directly. EF can discover related entities through navigation properties.

### 3. Register it

In `Program.cs`, add the project namespace and uncomment the existing registration:

```csharp
using Microsoft.EntityFrameworkCore;
using QualityTracker.Data;

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(
        builder.Configuration.GetConnectionString("DefaultConnection")));
```

Register each service beside it with a scoped lifetime:

```csharp
builder.Services.AddScoped<WorkItemService>();
```

`AddDbContext` is scoped by default, so one HTTP request receives one context. Do not keep a context in a singleton or a static field.

### 4. Set the connection string

The template contains a placeholder `DefaultConnection` in development and production settings. Never commit a real password. For local development, store it in .NET user secrets:

```powershell
dotnet user-secrets init --project .\QualityTracker.Server
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Server=...;Database=...;User Id=...;Password=...;TrustServerCertificate=True;" --project .\QualityTracker.Server
```

In a deployed environment, supply `ConnectionStrings__DefaultConnection` through the host's environment or secret store.

## Create and apply migrations

Install the EF CLI once if `dotnet ef --version` is not available. Keep its major version aligned with the EF packages in the server project.

```powershell
dotnet tool install --global dotnet-ef --version 10.0.10
```

After creating the first model and `AppDbContext`, run these commands from the repository root:

```powershell
dotnet ef migrations add InitialCreate `
  --project .\QualityTracker.Server `
  --startup-project .\QualityTracker.Server `
  --output-dir Data\Migrations

dotnet ef database update `
  --project .\QualityTracker.Server `
  --startup-project .\QualityTracker.Server
```

Whenever a model or EF configuration changes:

1. Add a migration with a specific name, such as `AddWorkItemDueDate`.
2. Read the generated `Up` and `Down` methods. Confirm that EF is not dropping or recreating data unexpectedly.
3. Apply it locally with `dotnet ef database update`.
4. Commit the model, configuration, and migration together.

To discard the most recent migration **before it has been shared or applied**, use:

```powershell
dotnet ef migrations remove --project .\QualityTracker.Server --startup-project .\QualityTracker.Server
```

Do not edit or delete a migration that other environments may already have applied. Add a new corrective migration instead. Production migrations should run as an explicit deployment step, with a backup for destructive changes; do not call `Database.Migrate()` on every application startup.

## Build a backend feature

For a `WorkItems` feature, add files in this order:

1. `Models/WorkItem.cs` and any EF configuration.
2. A reviewed migration.
3. `DTOs/WorkItems/CreateWorkItemDto.cs`, `UpdateWorkItemDto.cs`, and `WorkItemDto.cs`.
4. `Services/WorkItemService.cs`, registered as scoped in `Program.cs`.
5. `Controllers/WorkItemsController.cs`.

A controller action should be little more than routing, a service call, and the HTTP result:

```csharp
[HttpPost]
public async Task<ActionResult<WorkItemDto>> Create(
    CreateWorkItemDto request,
    CancellationToken cancellationToken)
{
    var created = await service.CreateAsync(request, cancellationToken);
    return CreatedAtAction(nameof(GetById), new { id = created.Id }, created);
}
```

Pass `CancellationToken` through async EF calls, use `AsNoTracking()` for read-only queries, and save once after all changes for a use case are ready. Avoid `catch (Exception)` in every controller; map expected errors centrally to consistent problem responses.

## Build a frontend feature

Keep code with the feature that owns it. A work-items page, form, API functions, and feature-specific hooks belong under `features/work-items`. Move something to `components` or `lib` only after more than one feature genuinely shares it.

Frontend rules:

- Call relative URLs such as `/api/work-items`; Vite already proxies `/api` to ASP.NET during development. Never hardcode a localhost or production hostname.
- Keep network calls in the feature's `api.js` (or a shared `lib/api.js` wrapper), not inside generic UI components.
- Let route-level pages coordinate loading, errors, and feature components. Keep shadcn/ui files in `components/ui` generic and free of business rules.
- Prefer component or feature state first. Add application-wide state only when several unrelated routes must read and update the same data.
- Treat API responses as untrusted input and show useful loading, empty, and error states.

Example feature API function:

```javascript
export async function getWorkItems(signal) {
  const response = await fetch("/api/work-items", { signal });

  if (!response.ok) {
    throw new Error("Could not load work items");
  }

  return response.json();
}
```

Add shadcn/ui primitives from the client directory, then compose them inside a feature:

```powershell
cd .\QualityTracker.client
npx shadcn add dialog
```

When adding React Router, keep route definitions under `src/app` and use `import.meta.env.BASE_URL` as the router basename if the deployed application lives below the domain root. The build base path can be set with `VITE_BASE_PATH`.

## Before committing

Run the checks from the repository root:

```powershell
dotnet build .\QualityTracker.slnx
cd .\QualityTracker.client
npm run lint
npm run build
```

Also verify new endpoints through `/swagger`, test both successful and invalid requests, and review any migration before it reaches a shared database.

## Deployment

`dotnet publish .\QualityTracker.Server -c Release` produces the deployable server and client output. `deploy.ps1` is an environment-specific IIS/file-share example; update its destination for the application before using it. Apply reviewed database migrations as a separate controlled step, then deploy the application.
